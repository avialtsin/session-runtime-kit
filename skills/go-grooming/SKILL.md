# go-grooming — груминг доски и репозитория

Груминг нужен, когда на доске хаос: много старых номеров, In Progress давно влито, непонятно, что
живое. Каждый груминг открывает новое **поколение** задач: живое переписывается новыми задачами,
старые активные уходят в архив со ссылкой на новые.

Скрипт — `~/.agents/skills/go-grooming/scripts/generation.py`, запуск из корня репозитория.

## Поколения

- Номер задачи: последние три цифры — задача, всё перед ними — поколение. `TASK-3001` — поколение 3,
  задача 001; подзадача — `TASK-3001.01`; поколение 12 — `TASK-12001`. В поколении до 999 задач.
- Поколение открывает **якорь** — `backlog/completed/task-N000 - Поколение-N-начало-нумерации.md` со
  `status: Done`. У `backlog task create` нет ключа номера: следующий номер — наибольший в `tasks/` и
  `completed/` плюс один, архив не считается. После якоря CLI сам выдаёт `N001`, `N002`…
- Якорь — единственная ручная правка файлов доски, её кладёт `generation.py open`. Всё остальное
  меняется только через CLI. Якорь не архивировать и не удалять: без него нумерация откатится к
  наибольшему номеру в `tasks/` и `completed/`.
- Префикс поколения (`G3-001`) не годится: Backlog.md 1.52 не даёт сменить `task_prefix` («Task prefix
  cannot be changed after initialization»), а смена в конфиге руками ломает поиск старых задач и
  номера подзадач (`TASK-G01-TASK-G01-001.01`).
- Новые доски (скилл `go-create-repo`) заводятся сразу с якорем `TASK-1000`. На старой доске без якоря
  номера до 1000 — «до поколений», первый груминг открывает поколение 1 или следующее за
  наибольшим номером.
- Архив CLI не видит: ни `task view`, ни `search`. Файлы лежат в `backlog/archive/tasks/` и читаются
  глазами. Поэтому новая задача должна быть самодостаточной, а не ссылкой «см. TASK-…».

```bash
python3 ~/.agents/skills/go-grooming/scripts/generation.py status
```

Покажет якоря, следующий номер, активные задачи по поколениям и предупредит, если поколение
подходит к 999 или в нём остались задачи прошлых поколений.

## Порядок

Сначала прочитать `AGENTS.md` проекта: проекты доски, правила веток, проверка перед коммитом, где
ядро и где модули. Груминг — сам задача на доске: завести её в текущем поколении. Материалы — в
`sessions/NNN-ДДММГГ_Груминг-…/` по правилам проекта.

### 1. Разбор — только чтение, не больше двух агентов

Два агента параллельно, каждый пишет отчёт файлом в папку сессии.

**Обзор доски** (`обзор-доски_v1.md`). Каждая активная задача сверяется с git, а не с заметками:

- влито ли — `git merge-base --is-ancestor <коммит> origin/main`, `git log --all --grep TASK-N`,
  `git cherry`;
- есть ли ветка и дерево — `git branch -a`, `git worktree list`, `orca worktree list`;
- выложено ли — выпуски проекта (`docs/releases/` или что указано в `AGENTS.md`).

Вердикт по каждой: сделано и не закрыто / живое / брошено / устарело / дубль. Где вердикт — догадка,
так и пометить. Отдельно — задачи, которые прямо сейчас ведут параллельные сессии (на них ссылаются
живые ветки и деревья, недавние правки): их груминг не трогает.

**Аудит репозитория** (`аудит-репозитория_v1.md`). Контекст — глобальный скилл
`agent-context-pipeline`, затем `repowise dead-code`, knip (для JS/TS), граф импортов от настоящих
точек входа; каждого кандидата на удаление проверить руками. Ещё: влитые и брошенные ветки, вес git,
дубли кода, устаревшие документы.

> Пайплайн RepoWise на время обновления индекса прячет каталоги из `.repowiseIgnore` прямо в рабочем
> дереве — параллельные сессии видят «удалённые» файлы. Запускать его в отдельном дереве.

**Материалы и решения** (скилл `go-board`) — в отчёт обзора доски: решения с одним заголовком;
заменённые, у которых нет статуса `superseded` и строки «Заменено»; `proposed`, которые давно ждут;
идеи без статуса. Отдельно — материалы вне доски, которые стоит выложить: принятые `тема_vN` в
сессиях, папки вроде `base/`, `pm/`, `second-brain/`, `wiki/`. Описание кода остаётся рядом с кодом.

### 2. Решения пользователя — одним вопросом

Свести из обоих отчётов то, что требует решения: что удалить из кода, какие ветки удалить, какие
невлитые сохранить на origin, что закрыть сразу, что в архив, какие материалы перенести на доску,
какие решения `proposed` принять. Задать одним вопросом со списком, не
по одному.

### 3. Уборка — свежими агентами по файлу отчёта

Исследователей с раздутым контекстом не продолжать: исполнение — новым агентам с коротким заданием
и ссылкой на отчёт (снова не больше двух).

- **Код** — в своём дереве и ветке от `main` по правилам проекта, проверка проекта перед коммитом,
  вливание.
- **Ветки** — перед удалением записать имя и хэш каждой в `удалённые-ветки_v1.md`; невлитые — только
  по решению пользователя.
- **Доска** — сделанное и выложенное закрыть сразу (`task complete`), оно сохраняет старые номера.

### 4. Продуктовые проблемы

Оставшиеся живые задачи перевести на язык продукта и оценить.

- **Проблема** — что видит пользователь, какие продукты, что поменять, где правка (по устройству
  проекта: ядро / модуль / данные / инфраструктура / решение), тяжесть, вид (сломано / риск /
  нехватка), из каких задач собрана.
- **Оценка** — трудоёмкость (просто / средне / сложно, с местом правки в коде), фундаментальный
  корень — изъян устройства, из которого растут две проблемы и больше, природа — продуктовая или
  техническая.
- Итог — HTML-страницы для спокойного просмотра: проблемы по продуктам и «просто / фундаментально /
  технически». Пользователь смотрит и соглашается со списком до создания задач.

### 5. Новое поколение

1. Якорь — и сразу отдельным коммитом в `main` с пушем, чтобы параллельные сессии после `pull`
   нумеровали с `N001`:

   ```bash
   python3 ~/.agents/skills/go-grooming/scripts/generation.py open --dry-run
   python3 ~/.agents/skills/go-grooming/scripts/generation.py open --note "Открыто грумингом ДД.ММ.ГГГГ: sessions/<папка>."
   git add backlog/completed && git commit -m "chore(backlog): open generation N" && git push
   ```

2. Задачи из проблем — через CLI (`backlog task create … --project … -p …`): эпик «быстрые правки»
   на одну ветку, эпики-корни с подзадачами-проблемами, остальное — отдельными задачами. В описании
   каждой — суть проблемы целиком и строка «Из поколения N−1: TASK-…». Много задач — скриптом в
   папке сессии с режимами `plan` и `apply` (образец — `generation3.py` там же).
3. Старые активные — в архив по карте «старая → новые» (JSON в папке сессии):

   ```json
   {"TASK-12": ["TASK-3001", "TASK-3004"], "TASK-40": "устарело: функцию убрали в abc1234"}
   ```

   ```bash
   python3 ~/.agents/skills/go-grooming/scripts/generation.py retire --map <карта> --dry-run
   python3 ~/.agents/skills/go-grooming/scripts/generation.py retire --map <карта> [--cascade]
   ```

   Скрипт проверит, что старые задачи активны, а новые существуют, допишет заметку «Поколение N
   (дата): переформулировано в TASK-…» и отправит в архив. Архив не уносит подзадачи сам: без
   `--cascade` скрипт перечислит подзадачи без решения. Задачи параллельных сессий в карту не класть.
4. `generation.py status` — прошлых поколений должны остаться только задачи параллельных сессий.
   Закоммитить доску.

### 6. Правило в AGENTS.md

Если в разделе проекта про доску нет правила поколений — дописать (по согласию пользователя):

```markdown
**Поколения задач.** Последние три цифры номера — задача, всё перед ними — поколение: `TASK-1001` —
поколение 1, задача 001; подзадача — `TASK-1001.01`. Поколение открывает якорь
`backlog/completed/task-N000 - Поколение-N-начало-нумерации.md` (`status: Done`): следующий номер CLI
берёт от наибольшего в `tasks/` и `completed/`. Якорь — единственная ручная правка файлов доски, его не
архивировать и не удалять. Когда доска запуталась или поколение подходит к 999 задачам, новое
поколение открывает груминг — глобальный скилл `go-grooming`.
```

И строкой — текущее поколение и с какой даты, какие старые задачи оставлены живыми.

### 7. Отчёт

Коротко по-русски: что найдено, что убрано (код, ветки с файлом хэшей), сколько задач закрыто, какое
поколение открыто, сколько создано и сколько ушло в архив, какие старые оставлены и почему, ссылки на
HTML-сводки.
